# Architecture snapshot

Zuno Edu is one education platform with five surfaces: public website, parent portal, student LMS, teacher portal and administration. All use the same application backend, domain model, authorization policies and PostgreSQL database. The launch baseline is the complete instructor-led education business defined by the product requirements. Native apps, social networking, unrestricted messaging, autonomous AI tutoring, marketplace payments, subscriptions and microservices are excluded. Scope remains draft until the human merges the identified planning PR.

The frontend uses Next.js App Router, strict TypeScript, Tailwind and shadcn primitives. Routes compose feature modules, which compose domain components and shared accessible UI. A generated contract package supplies API types and clients. Private data is not publicly cached; query keys include principal/resource scope and logout clears cached data. Route guards improve navigation, while the backend remains authoritative. Teacher/student bundles do not import financial administration. Learning follows Learn, Attend/Watch, Try, Build, Submit and Review/Reflect, using accessible responsive layouts and clear age-appropriate language.

The backend uses Python/FastAPI with a modular object-oriented domain. Entities protect identity and lifecycle; immutable value objects represent validated concepts such as money and time ranges. Application services authorize and orchestrate use cases. Repositories and integration ports invert dependencies; infrastructure adapters implement them. FastAPI routes contain transport work, not business rules or direct database/provider access. SQLAlchemy data mappers and Alembic are outside domain code. Durable public behavior must match the object, service, API and Code Blueprint catalogs; a material missing contract stops the affected chunk for explicit design resolution.

Program groups reusable courses. A published course revision contains modules, lessons, typed blocks and assessment definitions; cohorts pin revisions rather than duplicate curriculum. A cohort is a scheduled delivery, and a class session is one occurrence. Enrolment links student to cohort and governs educational entitlement. Teacher assignment narrows teaching authority, attendance tracks session participation, submissions preserve versions, and assessments/feedback have distinct draft/released states. Progress is calculated from required learning items and attendance; a completion certificate is the launch achievement. Numeric declared age and the date it was captured satisfy age collection without requiring date of birth; school and unnecessary profile details remain optional.

Parents have explicit authorized guardian relationships for educational access and family membership for billing. Students see their own released learning information and no financial data. Teachers see only assigned learners' educational projections and have zero financial administration. Administration separates identity, education, finance, operations and audit privileges. A teacher principal cannot gain finance by combining roles. Server sessions, staff MFA, resource ownership, relationship/state checks, scoped repositories and negative authorization tests enforce these boundaries. Public content is an explicit publication projection. Sensitive records are retained or purged by approved policy with legal holds and audit evidence.

Stripe hosted Checkout supports one upfront AUD payment per child/cohort. Server verification, capacity holds, ledger identities, refunds and reconciliation govern activation; redirects never prove payment. Zoom meetings mirror sessions behind LiveClassProvider, with host links restricted and fetched on demand. Google Calendar mirrors individual schedule events; PostgreSQL stays authoritative. Resend handles transactional emails through a durable notification ledger. S3-compatible private storage quarantines uploads and promotes verified immutable assets. The transactional PostgreSQL outbox/inbox and job leases preserve work; Redis supplies replaceable queue/cache support.

Deployment targets an OCI-compatible VPS with Docker Compose and Caddy HTTPS, private PostgreSQL/Redis networking, separate API/worker processes and external object storage. Staging uses synthetic data and separate provider credentials. CI enforces tests, contract/architecture checks and security scanning. Versioned releases, monitored health, off-host backups, isolated restore drills and rollback procedures are launch requirements. Human policies, tax configuration, provider accounts and operational ownership are explicit launch gates; no production service is deployed during bootstrap.
