# Backend architecture

Status: DRAFT. Architecture version1.0. This is a complete proposed launch blueprint for human review. No application code is implemented. Canonical machine-readable details: [backend-catalog.json](backend-catalog.json). Requirement authority: [requirements.json](../product/requirements.json). Implementing chunk IDs are assigned by the consolidated Code Blueprint and requirement-to-chunk traceability; no catalog entry may be implemented without that assignment.

Approved package layout is `apps/api/src/zuno_edu/modules/<capability>/{domain,application,infrastructure}` with shared entrypoints in `interfaces/api`, composition in `bootstrap`, and narrowly shared contracts in `shared`. Capabilities are identity, family, content, curriculum, delivery, enrolment, assessment, learning, billing, communication, files and operations. The Code Blueprint assigns each named object/service/port to a file; this document establishes dependency rules rather than implementing packages.

Dependency direction is interfaces→application→domain. Infrastructure implements application ports and imports domain types for mapping; domain never imports infrastructure. FastAPI routes parse a documented request, acquire Principal, call exactly one named public use case, translate a typed result/error and serialize the declared response. They contain no SQL queries, provider SDK calls, business rules or security exemptions. API DTOs are deliberate whitelists, never ORM serialization.

Domain entities own identity and meaningful transitions. Immutable value objects represent money, age snapshots, time slots and verified references. Closed enums encode lifecycle states. Pure policy objects decide access/release/completion from explicit facts. Application services orchestrate these policies, aggregate loading, UnitOfWork, integration intent and result projection. Composition is the default; no domain entity inherits an ORM base and no universal base service/repository drives arbitrary CRUD. Typed protocols describe ports. Repositories are aggregate-appropriate, not one per noun.

SQLAlchemy uses explicit external mappings and data mappers under each module's infrastructure persistence area. ORM row models and SQLAlchemy sessions never escape an adapter. Mapping verifies domain invariants when reconstituting aggregates. Read projections may use joined SQL with mandatory typed authorization scopes and explicit column lists. Alembic owns migrations. PostgreSQL is authoritative; Redis state can be destroyed and rebuilt without losing committed intent or financial/learning truth.

The composition root wires31 named service objects to31 ports and their concrete adapters. Request-scoped UnitOfWork controls database transactions; worker invocations use the same services with internal capability identity. Sessions, authorization context, validation errors, tracing, audit append and idempotency plumbing are reused through composition. Files, billing and integration jobs retain distinct policies rather than a universal upload/payment workflow abstraction.

Each mutating service authorizes, loads scoped state, validates preconditions and version, invokes domain behavior, and commits database changes/audit/outbox together. The service emits only the minimum event identifiers needed by workers. Provider operations execute outside database locks and use durable correlation/idempotency. Worker acknowledgements occur only after result persistence; failed claims expire safely. Stale provider mirror jobs compare desired version and cannot overwrite a newer schedule.

Contract validation must assert all307 explicit HTTP/worker operations and every referenced schema exist, enum types remain complete, IDs/method-routes are unique and no inaccessible projection leaks. Domain tests cover transitions and invariants, repository tests cover scope/constraints/transactions, application tests cover orchestration/negative roles, adapters cover retries/unknown outcomes and API tests cover actual serialized fields. Full launch test architecture and executable chunk gates are documented by the engineering standards.
