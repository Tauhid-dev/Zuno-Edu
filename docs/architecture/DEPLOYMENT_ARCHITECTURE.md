# Production and recovery architecture

Initial deployment is an OCI-compatible cloud VPS running Docker Compose. Caddy terminates HTTPS and routes /api/v1 to FastAPI, web routes to Next.js. Only ports 80/443 public; SSH restricted to operations network/keys. PostgreSQL and Redis are private containers/network endpoints. API and worker share packaged application code with different entrypoints. Worker executes durable PostgreSQL outbox jobs, with Redis as wakeup broker/cache. Production uses private S3-compatible storage with off-host encrypted backups. Domain/application code has no OCI dependency.

## Environment separation and supply chain

Local, CI, staging and production use separate databases, buckets, Stripe modes/accounts, Zoom/Calendar configuration, mail domains and secrets. Staging contains synthetic children, not copied production records. Versioned configuration schema validates required settings at startup and prevents test provider keys in production. Secrets injected at runtime via protected secret files/environment; no secrets in images, source, Docker build args or NEXT_PUBLIC variables. Pin supported runtime/package versions and container digests in the foundation chunk after compatibility/security review; commit lockfiles. Non-root containers, read-only root where compatible, capability drop, resource limits and minimal egress. CI pins third-party action commit SHAs and grants read-only default permissions.

## Build/release pipeline

PR: scope/traceability checks, lint/type checks, domain/application/authorization/repository/API/frontend tests, migration tests against real PostgreSQL, OpenAPI client drift check, component/accessibility tests, build, dependency/secret/container scanning. Integration secrets never run on untrusted fork PRs. Successful master build yields immutable tagged images and software bill of materials. Human-controlled deployment promotes tested digest to staging, applies migrations once, runs end-to-end smoke tests, then production approval and rolling/brief maintenance replacement on the VPS. No auto-merge.

Migration job uses exclusive advisory lock, application compatibility check and backup checkpoint. Expand-contract schema changes permit rollback to previous image; destructive migrations require separate approved data transition. API never auto-migrates at startup. Deployment runbook records image digests, configuration version, migration head, operator and test evidence.

## Reliability and observability

/health/live reports process liveness without secrets. /health/ready tests required database/schema availability; Redis/provider degradation is separately reported without making every provider outage restart the API. Worker heartbeat, queue oldest age, retries/dead letters, payment reconciliation mismatches, failed scans, backup freshness and provider error rate are monitored. JSON logs carry request/correlation IDs, operation/status/latency; no child names, notes, credentials, tokens, payment details or URLs with secrets. Error reporting scrubs payloads and identifiers. Append-only audit events have restricted access and separate retention.

Launch engineering targets: 99.5% monthly availability target excluding approved maintenance; read API p95 <=500ms and write p95 <=1s excluding uploads/external checkout at 100 concurrent authenticated users for 15 minutes. Authenticated navigation p75 LCP <=2.5s on a mid-tier mobile profile with 4x CPU slowdown and simulated 4G (1.6Mbps down/750Kbps up,150ms RTT). Test and record load profile in release gate; capacity can scale API/worker replicas before architectural redesign. Alert on 5xx >2% for 5m, API p95 >1s for 10m, oldest critical job >5m, backup age >24h or disk >80%. On-call owner/notification destination are required production configuration.

## Backup, restore and failure recovery

PostgreSQL encrypted daily full backups + continuous WAL shipping target RPO <=15m, RTO <=4h. Store backups off VPS, separate credentials, 35-day rolling retention. S3 versioning plus daily inventory/off-account copy of changed immutable assets target object RPO <=24h; retain 35 days unless approved per-class retention/hold requires longer. Financial retention duration is a human legal decision and must configure production before launch, not guessed as a legal obligation. Secret encryption key recovery is kept separately under operator control.

Monthly and prelaunch restore drill into isolated environment: restore DB snapshot then WAL to chosen point; restore matching object versions; apply privacy deletion tombstones; verify foreign keys, signed asset downloads, ledger counts/totals, pending outbox/inbox and provider bindings. Disable all outgoing emails/payment mutations during restore. Reconcile Stripe and provider state since restore point before reopening checkout/classes. Record elapsed recovery and achieved RPO, missing asset incidents and operator sign-off. Redis loss rebuilds from PostgreSQL; VPS loss provisions from versioned infra and restores off-host backups. External outage queues work and shows degraded state. Disk full stops writes safely and alerts. Rollback uses previous compatible image; restore backup only under incident runbook because it can lose post-backup writes.

Required launch evidence includes HTTPS/security headers, network exposure, secrets rotation, staging/provider smoke tests, backup/restore drill, alert delivery, rollback rehearsal and responsible operator contacts. Infrastructure skeleton in this bootstrap contains documentation only; no production deployment occurs.
