# Authorization model

Status: DRAFT. Architecture version1.0. This is a complete proposed launch blueprint for human review. No application code is implemented. Canonical machine-readable details: [backend-catalog.json](backend-catalog.json). Requirement authority: [requirements.json](../product/requirements.json). Implementing chunk IDs are assigned by the consolidated Code Blueprint and requirement-to-chunk traceability; no catalog entry may be implemented without that assignment.

Every decision combines principal role, explicit privilege, ownership, current relationship/assignment and resource state. Role-only authorization is insufficient. Deny by default. Authorization occurs at API entry, application use case and purpose-scoped repository query. Client route guards and hidden menus are presentation controls only.

`Principal` is an immutable server-created context: account_id, role, allowed admin privileges, account_status, authentication_time, mfa_verified_at and request_id. A limited MFA setup/challenge context is a different authenticated state with no portal privileges. JSON input can never set Principal, admin privileges, family scope or worker identity. Role/status/guardian/assignment revocation invalidates cached security context immediately; request scopes are resolved from current authoritative relationships.

A typed scope is a narrow immutable authorization result containing actor, purpose, allowed family/student/cohort/session IDs and applicable release state. FamilyScope/StudentScope/TeachingScope/BillingScope/AdminCapabilityScope cannot be built from a client-supplied family ID. Repository lookups include scope in SQL predicates; scope mismatch returns404 without distinguishing inaccessible existence. A principal with a prohibited capability, such as teacher requesting billing, receives403 before a financial query. Missing authentication receives401. Administrative privilege does not grant unrelated domain permissions.

## Role boundaries

Public reads only explicitly published safe page/course/cohort/instructor/event/policy projections. Student reads own educational data and released curriculum for active/completed entitled enrolments. Parent uses verified active child links for educational data and independent BillingMembership for finance. Teacher uses current cohort/session teaching assignment plus relevant learner enrolment and required teaching purpose. Administrator uses the exact privilege for the resource: identity_admin for accounts/family verification; education_admin for curriculum/delivery/learning; finance_admin for price/money/refund/reporting; operations_admin for nonfinancial settings/delivery health; audit_admin for redacted audit history.

A teacher principal cannot carry administrator privileges. Granting teaching plus financial privilege to one account is rejected and audited; a separate admin principal with mandatory MFA is required. Multi-privilege administrators receive only requested projections: education_admin does not read family billing and finance_admin does not read child assignment bodies. Integration configuration for Stripe requires both operations_admin and finance_admin. Replaying finance jobs also requires both. Grant modification cannot self-escalate or remove the last identity administrator. The initial human-authorized identity administrator is provisioned through a single auditable deploy command and immediately enrolls MFA; there is no public bootstrap-admin endpoint.

## Concrete authorization paths

Parent child creation requires verified active adult family membership, not a nonexistent-child link; creation adds initial verified link atomically. Family dashboards remain valid for zero children and return only individually linked children. Parent child progress, attendance, feedback and results require active GuardianStudent every read. Released marks/feedback only; no draft work body in parent submission status projection. Financial membership is checked again for every payment/document/refund read, independently of guardianship. An authorized billing adult still cannot pay for an unrelated child.

Teacher learner query joins teacher profile→active assignment→cohort/session→enrolment→student. The DTO excludes guardian contact, family identifier, school name, optional surname by default, money and credentials. Access expires on assignment revocation. Teacher rescheduling is assigned future session>=24hours ahead, valid DST and no participant conflicts; other changes require education admin with reason. Teacher host start is start−30minutes through scheduled end; student/guardian join is start−15minutes through end, with active enrolment and noncancelled session. Provider URLs are issued only after this check and never reused as host privilege for learners.

Student work writes bind student identity from session, validate enrolled pinned revision and release, and lock current work version. Student can update own preferred name/interests/experience, but not age, guardianship, financial membership or role. Quiz answer keys are never included before submission; own submitted results include correctness and approved explanation only. Teachers/admin can draft/release/withdraw assessment/feedback for permitted work; parent/student endpoints filter release in the query, not after broad serialization.

File access checks asset readiness, purpose and linked resource permissions before presigning. A public asset is public only through an explicitly published owner projection; tagging a private upload public cannot bypass the publishing process. Unready/rejected objects never receive download grants. Parent status views do not turn into submission authoring. Internal documents never become learner-visible because an admin attached them accidentally.

## Negative authorization proof

Required automated cases: teacher requests list/detail/export/refund/payment-file route→403; guessed foreign-family payment ID→404; revoked parent-child link→404; student guesses another submission/attempt/certificate→404; student requests billing/admin/settings→403; teacher requests unrelated roster→404; unassigned teacher uses known class host route→404; unreleased lesson/mark/feedback direct URL→404; private asset download before scan→409/404 without grant; expired or cancelled join→409; student controls family/role fields→422; limited MFA setup token requests admin dashboard→403; additive teacher/finance grant→409 and audited rejection.

Tests must exercise API serialization, service direct calls and scoped repository SQL; route manipulation, filter injection and stale cached relationships must not bypass decisions. Every privileged mutation records actor, action, target, timestamp, correlation and reason where documented, without secrets or full child work in audit payloads.

Production staff activation additionally requires canonical HG-STAFF approval evidence for initial administrators, role separation, teacher approval and incident contacts. No invitation or account-status operation may bypass this human gate. Full launch requires every canonical gate in LAUNCH_SCOPE, including HG-STAFF.
