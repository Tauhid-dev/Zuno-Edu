# Security architecture

Status: DRAFT. Architecture version1.0. This is a complete proposed launch blueprint for human review. No application code is implemented. Canonical machine-readable details: [backend-catalog.json](backend-catalog.json). Requirement authority: [requirements.json](../product/requirements.json). Implementing chunk IDs are assigned by the consolidated Code Blueprint and requirement-to-chunk traceability; no catalog entry may be implemented without that assignment.

The protected assets are child/family identity and educational work, credentials and role grants, payment truth, private teaching operations, integration secrets and auditable change history. Trust boundaries are browser→same-origin API, API/worker→PostgreSQL, durable queue→worker, provider webhook→ingress, and private storage/provider handoff→browser. Deny-by-default authorization and data minimization apply at every boundary. Security architecture is explicit technical design; legal/privacy wording and jurisdiction decisions remain identified human approval gates.

## Identity and session protection

Passwords are12–128 characters with breached-password screening and salted Argon2id hashes; implementation benchmarks parameters to a documented safe memory/time target. No plaintext password, session token or recovery code is stored or logged. Random sessions and purpose tokens have>=256-bit entropy and hashed lookup values. Cookies are Secure,HttpOnly,SameSite=Lax; CSRF token plus Origin check protects mutations. Session idle expiry30minutes for staff,12hours for parent/student; absolute expiry7days; rotate on login/privilege change/recovery. Password change, account suspension, privilege change and guardian-controlled child credential reset revoke affected sessions. Adult email verification precedes checkout or child credential activation; children require no email.

Mandatory teacher/admin MFA has durable `MfaFactor`, `RecoveryCode` and `MfaChallenge` state. TOTP seed is encrypted with a versioned managed key outside PostgreSQL; only ciphertext/reference is persisted. An audited library implements RFC6238 TOTP30-second intervals,6digits and ±1step tolerance; accepted timestep must strictly exceed persisted last step, checked under lock. Recovery codes have>=128-bit randomness, are shown once and only hashes are persisted. A recovery-code login consumes the code exactly once under the same transaction as challenge consumption/full-session issuance.

MFA challenge lasts5minutes with max5failures; invitation setup lasts10minutes and permits only enroll/confirm/logout. AuthOutcomeView explicitly carries challenge/setup state without a full privileged session. Verification branches on TOTP versus recovery code, obtains the appropriate proof through MfaVerifier, locks factor/challenge/code, rejects replay, consumes credentials and issues a new MFA-qualified session atomically. Setup URI is returned once over HTTPS/no-store and never logged. Lost-factor recovery uses unused recovery code; exceptional staff recovery requires human identity verification and audited identity-admin reset, session revocation and new MFA enrollment. No secret-removal bypass is exposed to a merely password-authenticated caller.

## Role, child-data and financial isolation

See AUTHORIZATION_MODEL, PERMISSION_MATRIX and DATA_ACCESS_BOUNDARIES for exact predicates. Parent-child authority and family financial membership are independent. Teachers have zero financial administration capability and no PaymentRepository dependency in teacher use cases. Additive teacher/admin role grants are rejected. Public/private/teaching/finance DTOs contain different columns. API filters, exports, dashboards and file grants all use the same current relationship rules, not cached claims alone.

Payment amounts, currency, price and merchant/tax snapshots are resolved server-side. Signature-verified provider events and server retrieval are authoritative. Webhooks use original bytes, timestamp tolerance300seconds and durable dedupe, support duplicate/out-of-order delivery and acknowledge only after durable inbox insertion. Checkout is one upfront AUD purchase for one student/cohort with a30minute capacity hold. Capacity updates, hold expiry and payment activation lock the same cohort. Late paid-no-seat exceptions never oversell and never auto-race refunds; explicit finance-admin ALLOCATE or REFUND locks decision, balance and seat. Refund is bounded by capture minus successful/pending refunds, idempotent and declares KEEP/CANCEL access. Teacher/student endpoints cannot read any part of the financial ledger.

## Input, files and provider secrets

Reject unknown fields, sanitize approved rich text before publication, use parameterized SQL and closed enums, bound page/range/body sizes and allowlist redirect/video hosts. Content Security Policy disallows arbitrary scripts/iframes; render text safely. CSV exports neutralize formula prefixes. Link/file paths use opaque references and safe basenames, preventing traversal. Outbound URL fetches disallow private/link-local/IP-literal targets and redirects outside approved hosts. Browser credentials never include database/object-storage/provider secrets.

S3-compatible storage is private and encrypted. Upload presigning reserves a unique quarantine key for5minutes. Student files<=25MiB each and<=100MiB total per submission, up to5files; staff documents<=50MiB and MP4<=500MiB. Allowed student types are PDF,PNG/JPEG,TXT and approved project ZIP; detected MIME, byte size and checksum must match. A sandboxed scanner rejects malware, encrypted archives, traversal links, executable payloads, expansion>100MiB, ratio>20,>100entries or any nested archive. Scanner unavailability fails closed. Only validated immutable promoted objects become ready. Download grants<=60seconds follow role/ownership/release checks; unready or held/purge-ineligible state never creates unrestricted access. Child archives are never executed.

Zoom credentials and meeting references are encrypted. Host handoff is fetched freshly only for assigned host within start−30minutes through end. Learner/guardian join is start−15minutes through end with current active enrolment. Waiting room enabled, join-before-host and automatic/local/cloud recording disabled. Parent receives no host URL. Calendar mirror contains no child roster or host credential. Email uses an approved authenticated business domain and minimum recipient/template fields; local idempotency outlives provider dedupe. Background retries preserve immutable intent, current source version and unknown-outcome reconciliation.

## Abuse, logging and audit

Initial configurable infrastructure limits: login5attempts/minute per identity plus broader IP controls; reset3requests/hour per identity; contact5submissions/hour per source; checkout10creates/hour per billing family; uploads20tickets/hour per student and bounded outstanding/quarantine storage. Responses remain uniform for unknown account recovery. Shared network limits supplement rather than lock out a whole classroom unnecessarily. Provider/webhook endpoints have independent byte/rate limits and alerting. Rate limit state is not identity authority; Redis outage fails safely for high-abuse operations.

Audit is append-only and records role/link changes, financial transitions/refunds, schedule exceptions, release/withdrawal, overrides/certificates, exports, settings and retention decisions. Append audit with the business transaction. Audit-admin read and export are themselves audited. No passwords,tokens,MFA seeds,host URLs,card data,raw webhook bodies or full child work appear in logs/audit. Raw verified webhook ciphertext has bounded retention; safe event IDs remain for dedupe. Operational dashboards return safe codes rather than raw provider errors.

## Production security and verification

Secrets live in environment-specific managed secret stores or protected deploy mounts with least privilege; never source, image layers, CI logs or application settings values. Database and Redis bind internal networks; only Caddy HTTPS ingress and controlled operator administration are exposed. Staging uses synthetic data and isolated provider accounts/buckets. Database/object/backups encryption and restore-only access apply. Credential rotation is versioned and tested, including webhook overlap windows and encrypted TOTP rewrapping. Readiness validates critical config without printing values; unapproved age/legal/finance settings block affected enrolment/publishing/purge.

Required proof includes negative role/resource tests at API/service/query layers, MFA setup and replay tests, CSRF/cookie/session revocation, concurrent seat/refund/exception tests, webhook duplicate/order/signature tests, upload malicious corpus and presigned-expiry tests, sanitized-content/redirect tests, log redaction, migration/restore integrity and dependency/container/secret scans. Critical/High exploitable findings block launch. Incident response follows operational runbooks, preserves safe evidence, revokes compromised credentials/access and records recovery without exposing live child data to development environments.

Primary reference constraints verified13September2026: [RFC6238](https://www.rfc-editor.org/rfc/inline-errata/rfc6238.html) supports time-step TOTP and replay prevention. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) sets the implementation floor for Argon2id at19MiB memory,2iterations and parallelism1; benchmark stronger values against target hardware. [OWASP authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) supports uniform error responses to resist enumeration. These are minimum technical controls; session and operational limits above are explicit product architecture decisions.
