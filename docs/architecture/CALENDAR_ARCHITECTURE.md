# Calendar architecture

SchedulingService owns finite recurring series expanded into individual ClassSessions. Store UTC start/end plus IANA zone and local scheduling intent. Reject nonexistent local times; ambiguous DST times require explicit offset selection. Session ID survives rescheduling; schedule version increments. A cohort schedule is created from a finite recurrence (weekly weekdays, local time, duration, start/end dates, explicit skipped dates) and previewed for conflicts before commit.

CalendarService uses CalendarProvider to mirror each class and audience-targeted business event into a dedicated restricted business calendar. Use deterministic provider event IDs derived from internal UUIDs with provider-valid encoding. Payload: public course label, session local/UTC start/end, zone, stable portal deep link and status. No pupil names, family data, attendance, payment data, host URL or participant list. Store calendar ID, event ID, etag, desired/applied versions. One provider event per occurrence prevents recurring exceptions from becoming a second schedule model.

On create/update/cancel, the transactional outbox schedules upsert/delete after commit. Conditional writes detect etag conflict and read the external record, then reapply the current authoritative domain state. External edits never import schedule changes. Missing event recreates it with the same deterministic identity. Cancellation removes the external event, retains local tombstone. Backfill/reconciliation enumerates domain sessions and compares bindings. If incremental sync is used and token expires with 410, rebuild only external mirror state; domain data remains untouched. [Google Calendar sync](https://developers.google.com/workspace/calendar/api/guides/sync).

Parent add-to-calendar uses authenticated per-session ICS export or Google add-event URL built from their linked child's schedule; no public subscription token. Include stable UID, SEQUENCE, timezone-aware times and portal URL. Downloaded static events cannot be remotely guaranteed to update: product labels the export as a snapshot and sends schedule-change notification pointing back to current portal schedule. Reminders are domain jobs at 24h and 1h before class and are cancelled/replaced when version changes. Calendar client reminders are optional user settings, not proof of platform notification delivery.

Verification: timezones including Sydney DST, duplicate upserts, out-of-order jobs, external deletion/edit, token expiry, cancellation, child/family export isolation and no sensitive provider payload.
